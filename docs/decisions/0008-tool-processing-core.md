# 0008 — Browser tools share a pure RGBA processing core and their own PNG encoder

**Context.** The plan asks for exact output dimensions, preserved alpha and
deterministic noise in the texture tools, and for downloads that match the
preview. Canvas `drawImage` resampling differs between browsers and GPUs, and
canvas encoders store pixels premultiplied, so a semi-transparent pixel can
come back one level off after `toBlob`. The owner's Seamless engine, on the
other hand, is defined by its canvas behaviour.

**Decision.**
- Seamless (T01) keeps the owner's canvas-based algorithm unchanged, ported
  line for line and proven byte-identical to `vendor/11am-seamless/engine.js`
  (ADR 0007, `tests/e2e/seamless-regression.spec.ts`).
- Every other tool works on plain straight-alpha RGBA buffers in
  `src/lib/processing` (resampling, quantising, dithering, blue noise), with
  no DOM, so the same code runs in Web Workers, in Node scripts and in unit
  tests, and gives the same bytes everywhere.
- PNG export goes through `src/lib/formats/png.ts`, a small deterministic
  encoder (fflate zlib, per-row filter choice). The file holds exactly the
  buffer that was previewed. JPG and WEBP use the browser encoder and are
  labelled as such.
- Seeded randomness only (`hash2`, `mulberry32`); blue noise is generated by
  void-and-cluster from a fixed seed.

**Consequences.**
- E2E tests compare downloads with the core run in Node on the same input,
  and with the on-screen preview, pixel for pixel.
- Decoding still goes through the browser (`createImageBitmap` and a 2D
  canvas), which is premultiplied: the alpha of each input pixel is exact,
  but the colour of a semi-transparent input pixel can shift by a few levels
  before processing starts. A JS PNG decoder would remove this; it is listed
  as a possible M09 improvement.
- Large images are processed on the CPU in workers. Limits are 4096² for the
  converter preview and 8192² for the resizer.
